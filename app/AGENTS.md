# AGENTS — app (manager backend)

Non-negotiable patterns for the manager backend. Read the root [../AGENTS.md](../AGENTS.md) first for the architecture and repo-wide rules; this file is backend-specific.

## Manager Networking (userspace Tailscale)

- Inbound tailnet traffic to the manager is delivered to `127.0.0.1:<port>` inside the container, so anything listening there (on `0.0.0.0` or `127.0.0.1`) is reachable from the tailnet wherever the tailnet policy allows. Never put an internal-only listener on `127.0.0.1`; use `127.0.0.2` or a unix socket.
- The container has no route into the tailnet: SSH to workers goes through `tailscale nc` (asyncssh `proxy_command`), for HTTP the workers reach the manager (Telegraf's reports and Vector's logs on 9001), not the other way round. Internet calls (Cloudflare, S3, ACME, GitHub) go direct.
- `sync_file` creates every file with its mode under a temporary name and renames it into place, so a reader never finds a partial file. A file with a secret in it goes with `mode=0o600` (a script `0o700`; the default is `0o644`): Tailscale SSH ignores the mode of a new directory, so the file's own mode is what keeps it private.
- Optional services (S3 `s3_config`, notifications) are checked before use: scheduled triggers skip quietly when unconfigured, user actions get a clear 4xx. Cloudflare is always configured; don't add checks for it.

## Services

- Services use the singleton base in `app/services/base.py`.
- Service mutations should remain thread-safe.
- Workers owns configured membership, infrastructure facts/writes and its read model. Observed IP/reachability/path belong to source-owned memory; durable Worker configuration holds hostname and subdomain. Worker projections read certificate state without mutating desired identities or material.
- Worker readiness requires a fresh coherent report and positive Traefik reachability evidence; startup grace never grants readiness without them. Reboot succeeds only after a confirmed host reboot, proven by host boot-ID change, and a ready worker. A missed deadline remains a failed task; later proof of the requested reboot and readiness returns the worker online, with failure history retained and no automatic repeat reboot.
- Container headline status and runtime knowledge are separate projections. When its worker is unreachable and no usable current observation remains, show headline error with unknown/unreachable runtime details and retain the last observation; do not turn that observation into proof the process stopped or is still running.
- Check preconditions before lifecycle effects. Worker availability failure aborts Deploy without stop/restart or target-proof invalidation. Once an intentional manual lifecycle action starts, execution failure calls for best-effort stop and headline error; a running observation does not erase that failure. Unexpected runtime exit/absence after a committed deployment is error, without automatic restart.
- Docker health is an independent runtime fact; ongoing health alone does not change headline status or routing. Preserve the deployment command's `--wait` readiness check.
- A Stop that cannot reach its worker fails and requires an explicit retry; do not persist deferred Stop intent. Interrupted volume restore leaves recovery error/details but permits an explicit Deploy after old work settles; no restore-before-deploy interlock is required.
- Manual backup requires a stopped container. Automatic backup preserves/restores its recorded pre-backup runtime on failure and after Manager restart; report backup failure separately when runtime is restored. Persist that workflow intent and prior runtime in the target record, and restore the applied deployment rather than newer saved config. Incomplete automatic backup is not handled as an interrupted deploy.
- Do not introduce alternate service lifecycle patterns without a clear reason.
- In-memory state derived from the DB or settings (setting values, the S3 client, notification config, the worker list) is refreshed wherever that data is replaced: a settings save, a restore.
- Storage work takes one `S3().session()` at its start and uses it to the end, its result included; a Backup row records the `storage_id` (`S3Session.identity`) it was written to, and work admitted under another identity is refused, never retargeted to the configured store.
- A consumer of a settings section (S3, Notifications) is installed from `Settings().snapshot(key)` by the workflow that saved or restored it and never reads Settings itself; a check result is recorded with the revision it checked (`Settings().record_check`) and counts only while that revision is current.
- Optional settings Save validates locally, persists configuration and checks the provider asynchronously. Save success, provider-check outcome and queue activity are separate facts; results certify only their matching configuration snapshot. Explicit Test evaluates its candidate values and declared test effects without saving them. Platform restore retains current S3 settings as an explicit input and prepares them before DB installation; other saved settings come from the backup.
- `Certs` owns desired identities, material, retirement and certificate status. Worker inputs hold only applied proof maps; derive validity/expiry/errors from `Certs`, independently for the worker wildcard and shared discovery. Issue/revoke only in the sequential global `{platform, app, domain}` maintenance operation (manager bootstrap runs serially before serving). Setup may distribute material or request maintenance. Retain retired public leaves until acknowledged revocation or expiry; no separate retirement queue/table/timer. Certificate templates belong to certificate proofs, not infrastructure stamps.
- `GET /api` is the `info` topic of the UI's Socket.IO connection, recomputed whenever one of its sources fires (a source fires only when what its owner holds differs, so a state that `info` shows needs a source), and the pause banner and the restore overlay rely on it, so it reads memory only: no network, no database.
- A Socket.IO topic is for a change the page did not make, so name that change before proposing one; a page's own action is shown by the page. The REST API stays complete: a route keeps every field whether or not a topic carries it. The rule with examples is in Pushed Updates in [docs/architecture.md](../docs/architecture.md).

## Logging And `task_id`

- `task_id` flows through `ContextVar` in `app/utils/logging.py`.
- The queue's `run_task` sets it for each queued task; a request has none.
- The offload helpers copy the context, so worker threads keep the originating `task_id`.
- Do not pass `task_id` through regular function parameters.

## Async Boundaries

- Offload blocking network/remote I/O — never `asyncio.to_thread()` (it runs on the default executor, outside the lane pools). Both helpers live in `app/utils/executor.py`:
  - `run_in_executor_with_context(...)` — awaited, from async code; offloads to the task's lane pool (ambient `active_executor`) or an explicit one, and raises if neither is set.
  - `submit_with_context(...)` — fire-and-forget, no running loop required (e.g. notifications).
- A queued task's lane is declared once at `add_task`; offloads inside it inherit it and don't re-name a pool.
- Fan-out orchestrators (`asyncio.gather` over offloads) must be async; never block a sync task on its own lane's pool — it deadlocks a single-worker lane.
- Local Peewee and SQLite calls run inline: SQLite on local disk is not an external call. Heavy file I/O is different (bulk writes in a loop, backup and restore copies, encryption, large listings): offload it, and write in one transaction (`db.atomic()`, `insert_many`) so the loop stays responsive.

## Database

- Main state is stored in SQLite with WAL mode. The database is deferred: `Database` opens it at `config.DB_PATH` at startup, and importing the models touches no disk.
- Models declare schema, storage conversion and constraints. Resource commands own dependent-field policy and explicit membership/counter/unlink transactions; save hooks/signals do not perform cross-resource effects. Re-fetch current IDs, merge explicit patch keys and write the affected fields. Publish only after the outer transaction commits.
- A resource command (`services/{applications,domains,workers}/commands.py`, built on `services/db/writes.py`) runs in its own `db.atomic("IMMEDIATE")` transaction and refuses to run inside another, publishes after its commit, and raises `ValueError` for an invalid value, `LookupError` for a missing row and `utils.errors.Conflict` for a duplicate or a refused delete.
- Pure value/codec imports do not initialize encryption or exit the process. Validate and initialize the encryption key explicitly at bootstrap before encrypted storage access; share scalar rules rather than duplicating validation across routes and models.
- Storage fields belong to `services/db/fields.py`, encryption to `services/db/encryption.py`, name/origin rules to `values/names.py` and key/value rules to `values/key_values.py`. Keep the DB package initializer free of model/signal loading; import schemas and initialization from their owning modules.
- Name everything Sage writes outside its database (worker files, markers, DNS record comments, archives) by the ID of the resource that owns it, with no instance prefix, number or mutable name: an opaque random ID, which stays the same across renames and recreation and does not collide between Sages, or for a worker its hostname, which is unique in the tailnet and is the Worker's primary key. Adding a worker is an explicit user action, so it cleans up, where required, what an earlier worker of that hostname left.
- A Container ID is an opaque placement identity: keep it across Deploy, Stop and Manager restart; allocate a fresh one on deletion/recreation. Instance.id establishes ownership; Instance.state_generation establishes installed configuration authority, stays stable across ordinary operation and gets a fresh value in a restored DB before installation. Target evidence must match both placement identity and generation; old-generation work cannot authorize resuming runtime after restore.
- A Volume rename preserves its identity and data. Worker storage and backup association follow stable Volume identity rather than the mutable name.
- Container and Worker event history survives resource deletion until normal history retention expires. Preserve its original subject identity/context independently of the live row; recreating a resource never reassigns old events or makes them runtime authority.
- Metrics are stored in per-host SQLite files.
- `Domain.container` owns a name's binding; use `Container.domains`, with no application-level domain collection. Enriched container responses share `routes.containers.container_payload`, and Domain fields share `routes.domains.domain_payload`. Domain changes and queue state notify the linked application and worker views.
- Times are naive UTC, the way the UI reads a timestamp that has no zone. Read the clock through `utils.common.utcnow()`; ruff (`DTZ003`, `DTZ005`) rejects `datetime.utcnow()` and a `datetime.now()` without a zone. Retry with backoff goes through `utils.retry` (`retry`, `retry_async`, and `is_transient` as the one meaning of "transient"); provider minimum waits belong to the error's numeric `retry_after_seconds`, which both retry helpers honor without adding attempts.
- Logs are stored in per-application SQLite files with FTS5 search; Traefik's access lines as requests in columns (`logs/requests.db`); a queued task's lines in `logs/tasks.db`, read by task id. The manager's other lines are in stdout only (`docker logs`).
- Preserve the existing lightweight storage approach unless the task explicitly requires otherwise.
- The live database (`data-gitignore/data.db`) is only ever read: open it with `sqlite3.connect('file:...?mode=ro', uri=True)`, and never run INSERT, UPDATE, DELETE or DDL against it. To exercise a write path, copy it to the session's scratch space and point `config.DB_PATH` at the copy.

## Migrations And One-Off Changes

- Do not add one-time migration/backfill/convergence code (DB rows, files, or external managed state like Cloudflare DNS records) just to bring existing deployments in line with a change. Prefer documenting the manual step in the summary/PR over shipping code that runs once and is then dead weight.
- The one sanctioned automatic migration is DB schema evolution — missing columns are added at boot and columns no model has are dropped (`Database` in `app/services/db/database.py`), in one transaction with foreign keys off. Anything beyond that (data backfills, external-state rewrites) is a manual step unless the user says otherwise.
- New writes should carry the new desired state going forward (e.g. a new default on create); reconciling what already exists is a documented manual action, not code.
- The upgrade itself is the release notes' too: what an existing install goes through while it moves to a change (a record gone before its replacement is written, a step to run first) never decides where code runs or in what order. Design for the final state.
- A schema change that existing data can refuse (a new unique index, say) stops the boot: Sage exits with one `[CRITICAL]` line holding what it knows of the failure and a link to the running version's release. The code prints no remediation; the release notes hold it, so it can be corrected without a release.
- Changing an existing column's type, `NOT NULL`, primary key, foreign key or `CHECK` (a new `ChoiceField` value included) is refused the same way on every existing database, since SQLite can't alter them in place. Such a change reaches existing installs only through the release notes' manual step, so name it there.

## Operation Queue And Scheduler

- APScheduler is a pure cron/interval trigger: each scheduled coroutine only calls `Manager().add_task(...)`. All execution and concurrency control live in the in-memory `TaskQueue` (`app/utils/queue.py`).
- Define corrective user actions by their resource-owned effects and verified completion goal. Worker sync and Traefik resync may be recomposed or split into infrastructure, certificate, routing and other corrections; their names do not require a single broad task. Each action preserves unrelated owners' evidence and uses the same owned operations as automatic convergence.
- Use literal `*` for a global queue exclusion rather than enumerating scope roots. It covers every queue task, including future roots; direct writes and ingestion still need their owning synchronization/lifecycle boundary.
- Platform backup captures a coherent SQLite configuration/history snapshot while operations continue. Disruptive worker infrastructure changes serialize against hosted container work on that worker; observations and work on other workers continue. Pool capacity and queue resource exclusion are separate concerns.
- Route and scheduled work alike enqueue via `add_task`; handlers take resource ids and immutable request values, not ORM objects. Re-fetch identity/membership at execution without replacing a frozen deploy-input snapshot with newer config. A target row deleted before the task runs is a legitimate interleaving: re-fetch with `get_or_none` and treat a missing row as a quiet no-op (log + return), never a crash.
- Scopes give hierarchical mutual exclusion (enforced by the dispatcher); their roots (`worker`, `domain`, `certificate`, `backup`, `discovery`, `settings`, `release`, `metrics`) are declared in `services/manager/queue.py`, and `*` needs no root. Lane pools are declared separately in `utils/executor.py`, and a task selects one executor independently of its scopes. `common` is a single-thread, low-priority lane (settings checks, log cleanup, release refresh): its tasks may wait, so nothing urgent goes there. A task's `key` is what its request competes for: its operation name, then its subject's ids and its intent (`("sync_domain", domain_id)`); requests that take turns on one subject share one, as a container's user lifecycle requests share `("lifecycle", container_id)` while automatic maintenance on it keeps its own; its `name` (the key's first part unless given) is what it does. Its scopes always include its subject's own scope. Admission is one `on_conflict` enum on `add_task`, comparing keys, never scopes: `DEDUP` (default: a pending or running task with the key does the request), `QUEUE` (always enqueue), `REPLACE` (latest wins: supersede the pending tasks with the key, even on other scopes, then wait), `REVISE` (busy while a task with the key runs, else as `REPLACE`). `add_task` returns accepted, existing (with that task's id), busy (with the running task's id) or refused. `cancel_tasks(key)` drops pending tasks only, never a running one or the restore. A task with another key on a conflicting scope never stops a new one: it defers behind it. A weaker background request and a stronger explicit one get different keys. `quiet=True` is for scheduled background housekeeping: no completed or cancelled row (the Task table is the history of operations worth debugging) and it never makes a settings section "applying"; a visible request with the same key makes the task visible. Details in [docs/backend.md](../docs/backend.md).
- A task's `params` are JSON-safe ids and flags, recorded and shown; frozen execution objects (a deploy snapshot, an S3 session) go in `inputs`, which are passed to the task and never recorded or pushed; `labels` name its subjects the way the UI does (`{"Application": "shop / web"}`), taken when it is queued.
- Task shape: one async task that `asyncio.gather`s its offloaded leaves (independent work in one operation, shared scope), per-entity fan-out (one `add_task` per entity, each with its own scope/lifecycle/DEDUP), or sequential `await`s (ordered/dependent steps). A fan-out parent must be async — never a sync task blocking on its own lane.
- Container crash recovery uses existing bounded worker command timeouts and normal reconciliation, without PID tracking or immediate targeted cancellation. Recovery may repeat containment stops; new remote mutations on that target wait for old work to settle and final runtime verification. This does not permit a live task to release its scope while its children still run.
- Declare intent, preconditions and success/failure/recovery postconditions with the owning operation. Apply the same contract during execution and recovery; variants belong in that declaration rather than backup/offline/startup exception branches or a second mutable registry. A failed pre-check is a rejected/not-started request, not a failed lifecycle transition. Append lifecycle history; a successful intentional action replaces the resource's prior failed result without rewriting its event.
- When adding or changing a task, declare its `key`, `scopes`, `executor`, `on_conflict` and `labels` at the single owning enqueue definition and **add/update its row in the [Task Catalog](../docs/operations.md#task-catalog)**, including its triggers and model writes. Update that reference's route/startup writers and model index when those paths change. Derive exclusions from the complete effect inventory, including inline calls; direct config edits require guarded results independently of queue scopes.
- Scheduler cadence lives in `app/scheduler.py` (`AsyncIOScheduler`): sub-minute pumps use `IntervalTrigger`, everything else uses `CronTrigger.from_crontab`. Gotcha: APScheduler's `from_crontab` treats numeric day-of-week `0` as **Monday**, while the `croniter`-matched per-app volume-backup crons use standard `0` = Sunday — be explicit about the intended weekday. `dispatch_tick` must stay `async` (coroutine jobs run on the loop; a sync job runs in a worker thread where its `asyncio.create_task` has no running loop).
- A scheduled or recurring task's external calls are budgeted (Cloudflare allows 1,200 calls per 5 minutes per user, across everything that user does): one list per check rather than a lookup per item, and writes only on drift. A task that a user's action starts runs rarely, so its calls aren't optimised for the rate limit.
- Sage never restarts or upgrades itself. Pause, restore and stop are a `TaskQueue` state (`Manager().pause_tasks()` etc.): paused, nothing starts but cron work still queues (DEDUP/REPLACE keep one copy each); restoring is paused except for the platform restore itself, and the UI is blocked; a stop signal drains (queued and later-added tasks cancelled, running ones finish). Routes use the Manager, not `scheduler` — only `main.py` imports it. While not running, `app/api.py` refuses changes with 503 (every method but GET/HEAD/OPTIONS, except pause/resume), so a route that only reads is a GET; pause comes only before a shutdown or an upgrade, so nothing else has to work while paused. See "Pause And Stop" in [docs/backend.md](../docs/backend.md).
- Verify task flow, logging flow, and async boundaries when touching orchestration code, including overlapping calls and a cache replaced while another thread reads it.
- A Domain owns its routing/DNS apply result and stable artifact identity. Its task holds `domain:<id>` and its linked app scope, validates that binding before I/O, and guards result writes against mid-run config edits. Queue facts project `syncing`; persisted results belong to the Domain. The parent cleanup/repair/discovery task holds `domain` and queues children without awaiting them. Child completion requests cleanup/discovery only; scheduled and external full scans own retries, so a failed child cannot form an immediate retry loop. Parent failures do not overwrite a Domain's successful apply proof.
- A failed saved Domain edit withdraws outdated owned routing where reachable and reports pending/error while leaving its Container runtime alone. Revalidate against current desired configuration before withdrawal; preserve already-correct artifacts and distinguish unreachable/unknown cleanup from confirmed removal.
- Domain `cors_origins` is a nullable validated list; blank derives that record's own current origin, while explicit references are manually maintained values. The effective list belongs in `DomainConfig` and its proof. Normalize only a dirty origins field so unrelated writes preserve concurrent policy edits. Keep application CORS separate from the shared discovery/probe policy; internal allow-lists run before preflight handling.
- Discovery derives availability from current Domain/container rows and the worker owner's cached ready set; it never runs status reconciliation or probes. All service-assigned names remain listed offline when unusable. `ApplicationMixin.save_container` owns active/non-active publication triggers. `worker_discovery` tracks the ready set that requested publication and is checked after ordinary worker pushes, outside worker locks; never check it from `_set_worker_tasks` or a queue-Fact callback, where enqueueing would re-enter a Fact lock. External changes request the full REPLACE pass so changes during an in-flight parent are retained.

## Testing

- Tests for the core engine (the task queue, the reconcilers and the status decisions) are exhaustive and may be slow: real scenarios on the real class (deploys and syncs crossing on shared scopes, restores, pauses, shutdowns) with mock task bodies, seeded random delays and failures, producers on several threads, and an independent model that predicts each admission and dispatch decision. Check the invariants and the model on every step, and plant bugs to see the tests fail. Correct admission is the main criterion, and scope exclusion the safety property. Mocks stand in for task bodies only, never for the decisions under test.
- A change that depends on how Sage is reached is tested through that shape: uvicorn serving TLS itself, as in production, and the Traefik image from `docker-compose.yml` terminating TLS in front of the real app (for a local run: on the host network, with a self-signed certificate and a router like the one in `dev/traefik/dynamic.yml`). Connect the way a browser does, send the proxy's headers per request type, and say what was and wasn't exercised. A "not verified" line in the docs is unfinished work.
- Check a change to `app/templates/worker/vector/vector.yml` with the workers' Vector image instead of guessing at VRL; Vector Config in [docs/development.md](../docs/development.md) has the commands.

## Don't

- Don't break `task_id` propagation.
- Don't replace the SQLite/WAL model with heavier infrastructure without a clear requirement.
